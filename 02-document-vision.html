Purpose and candidate models

The original Munera design calls for an evaluation-first OCR experiment, followed by task-specific training where necessary. OCR produces text; layout detection locates regions; table recognition reconstructs cells. These are distinct components in the Docling model catalogue.

Initial machine and training profile

Allocate this family time on the lab's shared GPU; purchase zero additional OCR GPUs initially. Run one training/evaluation job at a time. Proposed OCR allocation: 8 CPU equivalents and 32 GiB host RAM (8 GiB runtime + 8 decoding queues + 8 OS/agents + 8 headroom), not a measured minimum. The analytical case below makes a 24 GB device a qualification candidate; reuse the 80–96 GB device if the large-model route is selected. Leaseweb / ThinkOn prices and quote gaps.

For an independently operated OCR service, one L4 24 GB is a qualification candidate; do not buy it until OCR must run concurrently with large-model experiments. The official LightOn fine-tuning notebook reduces images to 700 px longest edge / 1,024-token cutoff and includes an optional rank-8 QLoRA path. It contains no executed peak-memory result. Start our pilot at microbatch 1, accumulation 4, activation checkpointing, with explicit language-only o/gate/up/down adapters and frozen vision/projector. This is a proposed adaptation; verify trainable module names and counts after initialization. Prefix-scope the language targets because vision modules can share projection suffixes. A suffix list alone does not establish frozen vision. PEFT target selection. Qualify the 1,540-pixel quality profile separately; reducing resolution can lose fine print. Paddle's ERNIEKit path also needs its own measurement.

TableFormer starts as a CPU job with 4 CPU-core equivalents and 16 GiB RAM allocated on the same worker, scheduled separately from OCR. This is a qualification allowance; its documented CPU support does not require another GPU.

GPU sizing arithmetic

Analytical sizing, not a measured peak or Daniel/security approval. Decimal GB = 10⁹ bytes; GiB = 2³⁰ bytes. Required device capacity is C ≥ (model state + saved activations + runtime workspace) / 0.8; leaving 20% free is our planning policy. Host RAM and disk cannot be added to VRAM without an explicit offload mechanism and performance trade-off.

The selected conservative mixed-precision Adam layout uses 18 bytes per trainable parameter: 2-byte compute weights + 4-byte master weights + 4-byte gradients + two 4-byte moments. Some implementations use 16 bytes instead; inspect the actual precision layout. For adapters, our 18-byte allowance is FP32 parameters/gradients/Adam (16 bytes) plus a possible 2-byte compute copy; PEFT can compute directly with FP32 adapters, so that copy is not guaranteed residency. PEFT dtype guidance. Frozen BF16 base weights use 2 bytes/parameter and have no base gradients/Adam state. LoRA state is base bytes + 18 × trainable adapter parameters. Memory accounting, LoRA parameters.

Selected job: LightOnOCR, frozen vision/projector, language-only rank-8 adapters. From the exact configuration, A = 28 layers × rank 8 × [(2,048+1,024) + 3×(1,024+3,072)] = 3,440,640 trainable elements for o/gate/up/down. Therefore adapter training state is 18A = 0.061932 GB. The published 2.011367489 GB checkpoint is a serialized base-weight proxy; actual tensor/loading dtype must be checked separately.

Image resolution changes the arithmetic. For square LightOn pages, patch size 14 gives Nvision = (edge/14)²; the 2×2 merge yields approximately Nvision/4 language image tokens, plus delimiters. At 700 px: 2,500 patches / 625 image tokens. At 1,540 px: 12,100 patches / 3,025 image tokens. Eager-attention diagnostic only, not a procurement memory requirement: one explicitly materialized BF16 vision attention-score tensor uses 2 bytes × 16 heads × Nvision²: 0.200 GB versus 4.685 GB per layer; an FP32 score tensor doubles these values. This is one tensor, not a complete peak. Efficient attention can avoid materializing it; selecting SDPA still requires checking the backend actually dispatched. A portrait-grid example differs from the square case: 1,190×1,540 pixels gives 85×110=9,350 patches, and approximately 43×55=2,365 merged tokens if the processor pads the odd grid. Record actual processor outputs rather than assume one page aspect ratio. Frozen vision under no_grad does not retain all 24 layers for backward; training vision changes that significantly. Pixtral vision implementation.

A text cutoff of 1,024 must not be read as a 1,024-token total after image expansion: 700-pixel square pages alone contribute about 625 visual positions. Log processor-expanded length and enforce the actual total. Keep the 1,540-pixel quality case separate. PaddleOCR-VL full tuning and TableFormer CPU execution are alternatives, not additional mandatory GPUs; Paddle's exact trainable recipe must be sized independently. Dataset size anchored to published OCR cases

LightOn's Arabic adaptation used 12,000 synthetic pages; its article does not disclose matching GPU, split or training time. This supports an adaptation-scale analogue, not a French accuracy guarantee. Our base adds 1,500 validation and 1,500 independent test pages, totalling 15,000. Low is 3,000/375/375; an optional high comparison uses 63,349 training table examples plus 7,919/7,919 holdouts, based on Apoidea's actual training log. Table crops are not interchangeable with full pages.

At an assumed 0.5 MB compressed image and two retained versions: 15,000×0.5 MB×2 = 15 GB. A decoded 700×700 RGB image is exactly 1.47 MB at 8 bits/channel, so two uncompressed versions would instead be 44.1 GB. Compression is a visible sensitivity, not a model requirement. Adding the existing 5 GB source-PDF placeholder, checkpoints and metadata gives 24.027345077 GB durable family assets; low/high are 12.777 / 88.214 GB. Additional production PDFs/pages are a separate variable. Pricing reconciliation.

For 12,000 training pages, three epochs and effective batch 4, 3×ceil(12,000/4)=9,000 optimizer updates. GPU-hours additionally require the actual expanded visual/text sequence lengths and implementation throughput; image count alone cannot supply them.

Recipe qualification and training work

Test native/high-resolution pages, optimized attention and larger microbatches after the minimum-memory smoke test. The Sinhala experiment reports LightOnOCR QLoRA on RTX 4090, NF4, rank 32 and 1,540-pixel input with 707 training pages. It is not our language-only rank-8 recipe or a universal 16 GB fit proof. Its compared runs change rank/dropout as well as resolution, so CER differences cannot be attributed solely to resolution or transferred to French documents.

The 15.092 GB value above is an 8 GB activation-sensitivity scenario, not a measured microbatch-1/1,540-pixel peak. Qualify larger microbatches using exact-recipe peak-memory logs. Current PaddleOCR backend, precision and sm_120 compatibility require their own forward/backward test; an older unsupported-backend report is not a timeless product limit. Paddle runtime guidance.

Training work: 12,000 training pages × 3 epochs = 36,000 page-passes. Training hours = page-passes × measured seconds/page-pass ÷ 3,600, plus evaluation and checkpoint time. Publisher inference at 5.71 pages/s on H100 is an inference benchmark, not a training rate. LightOn card. Record production pages/day, peak arrivals, image resolution and output length before sizing warm endpoints.

Pipeline and phases

This is a design mapping, grounded in Munera's pipeline and Google's levels 0, 1 and 2, not evidence that those levels are implemented. Framework owns the complete maturity criteria.

PhaseWork and release evidence
P0–P1 / manualEvaluate approved scanned documents against reviewed text/table labels. Preserve the original document, rendering configuration, candidate revision and evaluation output.
P2–P4 / preparation stageValidate labels and document provenance; isolate the frozen evaluation slice; version dataset manifests and render settings.
P2–P4 / training and evaluation stageRun the selected model's supported trainer. Compare candidate/incumbent text and table outcomes; retain configuration, run metadata and reviewer decision.
P2–P4 / serving stageDeploy the approved parser release through the model-specific runtime; retain a rollback release and feed reviewed corrections into the next dataset version.
P5 / CI/CDTest and package preprocessing/training/evaluation components; promote pipeline releases with automated regression checks and the retained approval gate.

The table separates stages within the existing P2–P4 pipeline grouping; it does not assign a new individual phase or calendar to each stage. One generic LLM trainer is not claimed to support every OCR/layout component.

French images and retained assets

SynthDoG's implementation generates document images with corresponding text using rendering and layout rules. Its published multilingual examples cover English, Chinese, Japanese and Korean—not a validated French dataset. French templates, fonts and domain labels remain Munera work. This differs from diffusion training, which trains a text-conditioned image generator. No diffusion checkpoint or workload has been selected in this design.

Store source documents, labels, rendering manifests, accepted page images, evaluation outputs and selected model releases. For adapter training, PEFT saves adapter weights/configuration separately from the required base model. The quantified pilot above uses explicit example volumes and retention; replace them with measured corpus statistics before production procurement.

Published experience and its limits

  • IBM, operational use: IBM Research reports using Docling to prepare InstructLab data and process 2.1 million PDFs. That establishes an actual document-processing use case, not Munera throughput or storage sizing.
  • NAVER, research implementation: Donut/SynthDoG publishes receipt extraction, document classification and document-QA experiments. Its GPU counts describe those experiments, not our OCR candidates.
  • LightOn, targeted adaptation and operational use: its Arabic adaptation report describes 12,000 synthetic training pages and separately identifies OCR2 in Console ingestion. It does not establish Québec document accuracy or L4 memory requirements.

Qualification gate: select the parser and approved French corpus; record peak RAM/VRAM, pages/s, quality, actual saved bytes and a restore test under the stated profile. Begin with the shared worker and conditional storage envelope above; add hardware only for measured capacity or independent availability needs.
