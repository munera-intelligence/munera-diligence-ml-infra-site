Retrieval — BGE-M3 embeddings and LightOn reranking

Updated 24 September 2026. Published facts are linked inline. Calculated scenarios and planning assumptions require workload qualification; they are not measured capacity or approval.

Research record · B2 · sources checked 24 September 2026 UTC. Munera's original design groups these components into an evaluation-first retrieval experiment. It does not establish that either requires additional fine-tuning. Their functions differ: BGE-M3 produces retrieval representations; LightOn scores retrieved query–document pairs. Published fine-tuning procedures

BGE-M3: FlagEmbedding accepts query/positive/negative JSONL and optional teacher scores. Its current M3 example uses an unfrozen encoder, unified dense/sparse/multi-vector training, self-distillation, FP16, gradient checkpointing, two processes, 512-token queries/passages, groups of eight, per-device batch two and two epochs. The code is an example; GPU model and VRAM are unspecified. It is not an 8K training qualification. Official embedder fine-tuning instructions

LightOn PW: the publisher reports joint text/vision rsLoRA with rank/alpha 32, learning rate 1e-4 and one epoch; released weights merge the adapter. The pointwise scoring target is Yes/No relevance for each pair. That is a different objective from BGE contrastive embedding training. Exact PW model recipe

The LightOn PW runtime contract requires Transformers ≥5.4.0 and Sentence Transformers ≥5.4.0 for CrossEncoder use. Preserve its fixed templates and first-position logit(Yes) − logit(No) scoring; these are upstream prerequisites, not a tested Munera deployment.

GPU sizing arithmetic

Analytical sizing, not a measured peak or Daniel/security approval. Decimal GB = 10⁹ bytes; GiB = 2³⁰ bytes. Required device capacity is C ≥ (model state + saved activations + runtime workspace) / 0.8; leaving 20% free is our planning policy. Host RAM and disk cannot be added to VRAM without an explicit offload mechanism and performance trade-off.

The selected conservative mixed-precision Adam layout uses 18 bytes per trainable parameter: 2-byte compute weights + 4-byte master weights + 4-byte gradients + two 4-byte moments. Some implementations use 16 bytes instead; inspect the actual precision layout. For adapters, our 18-byte allowance is FP32 parameters/gradients/Adam (16 bytes) plus a possible 2-byte compute copy; PEFT can compute directly with FP32 adapters, so that copy is not guaranteed residency. PEFT dtype guidance. Frozen BF16 base weights use 2 bytes/parameter and have no base gradients/Adam state. LoRA state is base bytes + 18 × trainable adapter parameters. Memory accounting, LoRA parameters.

Embeddings and reranking are separate training jobs. For the BGE-M3 recipe, account for every encoded passage, not just the query. Our example uses one query + four passages = five sequences per query group, each capped at 512 tokens. A trainer's train_group_size may count passages only; map the actual argument accordingly.

Dataset size anchored to published retrieval cases

The official MIRACL splits have 4,006 French+English training queries and 1,142 dev queries. Our base rounds this to 4,000 train / 1,200 validation / 1,200 independent test queries; the additional test set is our policy. Low uses 1,000/300/300; high uses 8,000/2,400/2,400 only if two distinct reconciliation tasks need separate coverage.

One positive plus three negatives gives 16,000 PW training pairs from 4,000 queries, not 16,000 independent questions. BGE encodes the query plus those four passages: 4,000×5×512×3 epochs = 30.72M positions. PW scores query/passage pairs: 16,000×512 combined tokens×3 epochs = 24.576M positions. These recipes have different token counts even when they share relevance labels. Publisher's PW objective.

For an initial searchable pool, 17,600 documents × six passages = 105,600 indexed passages. Six is a transfer proxy from MIRACL's approximately 5.71 English / 6.29 French passages per article, not an observed construction-document ratio. Production/unlabelled documents are additive. A published BGE-M3 adaptation used 854 training examples, 371,688 indexed passages, one RTX 3090, FP16, microbatch 1 and accumulation 4; sequence length is not disclosed and conflicting epoch times are excluded from our budget.

Using all 6,400 supervised queries, 105,600 chunks and existing retention: 32.370987263 GB family assets; two dense vector copies total 105,600×1,024×4×2 = 0.8650752 GB. The separate graph reserve is 0.4325376 GB, a policy allowance rather than measured Qdrant usage. Low/high family totals are 31.286 / 34.652 GB before that graph reserve. Pricing reconciliation.

Runtime and software qualification

Qualify checkpointing, efficient attention and PW hybrid-attention kernels on the actual GPU. Use recipe-matched memory and timing logs; results from different models, sequence lengths or kernels do not establish this configuration’s fit or runtime.

Base BGE work is 60,000 encoded sequences at 512 tokens = 30.72M positions; PW is 48,000 query/passage pair-passes at 512 combined tokens = 24.576M positions. Each selected embedding revision also needs a versioned 105,600-passage re-embedding and index build before rollout. Quote these as separately measured stages. Record queries/second, rerank depth, image share and latency before buying serving replicas.

Munera workflow and phase mapping

Existing design: versioned dataset → validate/prepare → optional tuning → frozen evaluation → approval → registry → serving → feedback, orchestrated through Airflow with DVC and MLflow. Its model experiment starts with evaluation. Munera design, §2–4

Family-specific upstream operations: documents are encoded for retrieval; queries retrieve candidates; the reranker scores those candidates. For tuning, positive/negative examples and optional distillation scores are separate inputs. These operations are documented capabilities, not a claim that Munera's vector database, reindex rollout or serving integration already exists. BGE example, LightOn retrieval description

Published experience

  • BAAI research: BGE-M3 evaluates multilingual, cross-lingual and long-document retrieval, including different retrieval representations. Benchmark results do not establish Munera recall. Original paper
  • LightOn engineering: the authors report unsuccessful listwise speed optimizations and measure the effect of reducing candidate depth. This is evidence to preserve the distinction between PW and LW methods when comparing costs. Field notes
  • Airbnb production: its two-tower system computes listing embeddings offline and query embeddings online. Frequent updates and filtering influenced its choice of IVF over HNSW. This is a production retrieval case, not BGE-M3 adoption. Airbnb engineering report

Production acceptance: confirm corpus/chunk count, retrieval modes, relevance labels, page-image share, rerank depth, throughput/latency and retention. Measure peak GPU/host memory, an optimizer step, index rebuild and checkpoint restore within the proposed pilot envelope before increasing concurrency or signing capacity commitments. Shared database/isolation roles live in infrastructure, and supplier configurations in pricing.
