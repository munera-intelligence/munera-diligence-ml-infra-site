Initial machine and operating limits

Proposed quote target: one shared 80–96 GB class GPU; 48 GB is an experimental alternative only after the loader/dtype test below. Evaluate one candidate at a time. Sequential scheduling is the simple baseline, not a hardware inability to share the board. Independent serving, MIG and concurrency require their own qualification. Request 64 GiB streaming-only and 128 GiB merge/cache-capable host-RAM alternatives from Leaseweb / ThinkOn, with 16 CPU equivalents as a planning allocation.

Host RAM scenarios: a CPU-resident 62.133 GiB BF16 base + 8 GiB OS + 8 GiB staging + 8 GiB decoding is 86.133 GiB before overhead; a 128 GiB quote gives headroom for that loading/merge route. Streaming to GPU can reduce host residency, so qualify a 64 GiB alternative. Low-memory loading supports reducing copies, not a universal host-RAM guarantee.

For QLoRA, qualify microbatch 1, accumulation 8, rank 16, 2,048 total tokens, one image ≤262,144 pixels, frozen vision/projector and activation checkpointing. Unsloth supports Qwen3-VL adaptation, but this precise profile is our proposal, not its measured benchmark. The actual mixed 4-bit artifact totals 32.260785502 GB, not the idealized 32B × 0.5 = 16 GB. File size is not runtime VRAM. A 48 GB quantized or 80 GB GPU alternative needs the same fit test; 48 GB cannot hold the unquantized Qwen tensors.

GPU sizing arithmetic

Analytical sizing, not a measured peak or Daniel/security approval. Decimal GB = 10⁹ bytes; GiB = 2³⁰ bytes. Required device capacity is C ≥ (model state + saved activations + runtime workspace) / 0.8; leaving 20% free is our planning policy. Host RAM and disk cannot be added to VRAM without an explicit offload mechanism and performance trade-off.

The selected conservative mixed-precision Adam layout uses 18 bytes per trainable parameter: 2-byte compute weights + 4-byte master weights + 4-byte gradients + two 4-byte moments. Some implementations use 16 bytes instead; inspect the actual precision layout. For adapters, our 18-byte allowance is FP32 parameters/gradients/Adam (16 bytes) plus a possible 2-byte compute copy; PEFT can compute directly with FP32 adapters, so that copy is not guaranteed residency. PEFT dtype guidance. Frozen BF16 base weights use 2 bytes/parameter and have no base gradients/Adam state. LoRA state is base bytes + 18 × trainable adapter parameters. Memory accounting, LoRA parameters.

Reference job: Qwen3-VL-32B QLoRA, language-only rank 16. For all seven language projections, A = 64 × 16 × [2×(5,120+8,192) + 2×(5,120+1,024) + 3×(5,120+25,600)] = 134,217,728 adapter elements. Adapter state is 18A = 2.415919104 GB. GQA projection shapes and the vision encoder make the classic encoder activation equation inappropriate here. Pinned model config.

Reading the safetensors headers of all seven pinned quantized shards gives an exact serialized tensor payload: 20,283,834,848 BF16 bytes + 6,045,376 F32 bytes + 11,970,537,982 packed U8 bytes = 32,260,418,206 bytes. Adding adapter state gives 34.676337310 GB. File headers are an additional 367,296 disk bytes, not GPU tensors. This is a tensor-placement baseline, not an exact resident peak: loader-created quantization state, compute casts and dequantization workspace remain additional. In particular, 32B × 0.5 = 16 GB misses the selected artifact's mixed precision. Quantization behaviour.

Device-visible memory can differ from marketed GB; obtain bytes from the actual board, convert MiB with ×2²⁰, and apply the reserve once. NVIDIA-SMI memory definitions.

Full fine-tuning is a different order of cost. A nominal 32B dense model has 32B × 18 = 576 GB of Adam state before activations. Dividing by a 96 GB device's 76.8 GB policy budget gives a state-only lower bound ceil(576 / 76.8) = 8 GPUs. This is neither a fit guarantee nor a purchase recommendation: real parameter count, unsharded layers, activations, collectives and gathered weights increase requirements. ZeRO stages. Ordinary DDP replicates the model; it does not pool GPU VRAM.

The 2,048-token run contract includes image-expanded positions. For a 512×512 image and 16-pixel patches, there are 1,024 vision patches and approximately 256 language image tokens after 2×2 merging, plus delimiters; confirm the processor's actual resizing and output. Microbatch 1 × accumulation 8 × one GPU gives effective batch 8. At 6,251 accepted training examples and three epochs: 2,346 optimizer updates and at most 38.406144M processed positions at 2,048 padding. Corpus size changes total work, while this microbatch/shape contract determines memory.

Other large models are substitutes, not concurrent purchases. Their nominal full-Adam state floors are 24B×18=432 GB for Mistral, 30B×18=540 GB for Granite, and 23B×18=414 GB for Luciole, before activation/runtime. Inference cache and concurrency

Using Qwen's configuration and vLLM's cache dimensions, BF16 KV bytes/token = 2 × 64 layers × 8 KV heads × 128 dimensions × 2 bytes = 262,144.

  • One 8,192-token live sequence: 2 GiB KV + 62.133 GiB base = 64.133 GiB, before runtime/vision overhead.
  • Four 8,192-token sequences: 8 GiB KV + base = 70.133 GiB, before that overhead.
  • Four 32,768-token sequences: 32 GiB KV + base = 94.133 GiB; approximately 101.075 decimal GB, exceeding a nominal 96 GB budget before runtime.

Tokens include cached prompt/image/output positions. Exclude block rounding, profiled activations, vision, CUDA graphs and runtime workspace before assigning remaining memory to KV cache. The current vLLM documentation lists gpu_memory_utilization=0.92; set it explicitly for the pinned release. It is separate from our 20%-free training policy. A memory-limited session count is not a latency guarantee. Start with a measured one/four-request workload, then decide whether serving needs a separate device or a qualified partition.

Dataset size anchored to published reasoning and extraction cases

FinQA has 6,251 training / 883 validation / 1,147 test questions, derived from 2,789 report pages. TAT-QA provides a larger comparison: 13,215 / 1,668 / 1,669 questions over 2,757 table-plus-text contexts. ConvFinQA separates conversations from turns; turns must not be counted as unique source pages. These financial QA tasks inform scale, not proof of French construction cross-document reconciliation.

Use the FinQA split as the base acquisition scenario, TAT-QA as high, and a no-additional-training evaluation path as low. Base: 6,251×3×2,048 = 38,406,144 processed positions and 3×ceil(6,251/8)=2,346 optimizer updates at effective batch 8. Nominal frozen 32B linear-layer work is 4×32B×38,406,144 ≈ 4.916×10¹⁸ FLOPs, plus adapter work; attention, vision, recomputation and quantization are additional. This operation-count approximation does not establish hours or hardware throughput.

At 8 kB per structured example, two retained versions of all 8,281 examples use 0.132496 GB. Keeping the same base/adapters/report policy gives 71.873940712 GB durable family assets; low/high 71.774 / 72.006 GB. The images are referenced from the shared OCR corpus, counted once. Runtime evidence and software qualification

Published comparable: Fixstars tested text-only Qwen3-32B on RTX PRO 6000 Max-Q 300 W; its logger reports GiB despite GB labels, and its recipes differ in batch size. It does not validate Qwen3-VL on Server Edition, a 64 GiB host, or the proposed BF16 LoRA peak. Its speedups are not inserted into the budget.

GPU-hour forecast: use the training-work calculation above with recipe-matched seconds/step, evaluation and save/reload times. Vendor peak FLOP/s and assumed utilization do not establish runtime. Use approved GPU-hour spend caps until the benchmark is available.

Qualify sm_120 before purchase. NVIDIA identifies the board's compute capability; PyTorch 2.7 introduced Blackwell/CUDA 12.8 support, and bitsandbytes builds list sm120. This does not certify the whole pinned stack. Test the exact supported driver, torch/CUDA image, loader, PEFT, attention backend, PW hybrid kernels, training save/reload and serving. FlashAttention's current support list is version-specific; do not carry forward a blanket claim that Blackwell has no accelerated backend.

The vLLM FP8/CUDA-graph issue 41651 is a specific fixed configuration issue; 45101 concerns FP8 MoE, not proof this dense model fails. Quote an H100-class fallback from the same two suppliers if available. Scope qualification labour separately in the pricing guide.

Supported methods and model portability

Qwen's trainer exposes LoRA and separate vision/projector/language tuning controls. LLaMA-Factory lists Qwen3-VL-32B support, SFT and adapter methods; its inspected Granite table lists 1–8B variants, not explicit Granite-4.2-30B qualification. Its generic memory estimates do not resolve that gap.

Bitsandbytes documents 4/8-bit training for additional parameters, not arbitrary full-weight quantized training. Model portability therefore includes compatible processors, chat templates, target modules and save/reload behavior—not just changing a repository name. PEFT's checkpoint format makes the base-model and adapter relationship explicit.

Pipeline and phases

The following is the existing Munera design, organized against Google's manual, pipeline-automation and CI/CD levels. These are target behaviors, not verified implementation status; Framework holds the common requirements.

PhaseWork and evidence
P0–P1 / manualEvaluate the unmodified candidate on the frozen French/English extraction set; record exact input preparation, template, output schema and model revision.
P2–P4 / preparation stageValidate approved examples, deduplicate, preserve document lineage and version the training/evaluation split. Route text and page images through their respective processors.
P2–P4 / training and evaluation stageRun a supported SFT/adapter recipe; retain configuration and metrics; compare with the incumbent and obtain the design's human approval.
P2–P4 / serving stagePublish a release manifest, restart/deploy the approved runtime/model, verify readiness and retain rollback. Measure the requested concurrent workload.
P5 / CI/CDPackage and test pipeline components; run regressions before pipeline/model promotion; connect production quality findings to reviewed future datasets.

MLflow aliases identify registered versions; the design also requires deployment orchestration. vLLM's LoRA documentation describes adapter serving and warns against unrestricted dynamic adapter loading. An alias reassignment is not proof that a running server loaded the new artifact.

Actual published examples

  • Apoidea/AWS, customer-coauthored experiment: the May 2025 banking-document study tunes Qwen2-VL-7B with QLoRA/LLaMA-Factory and serves through vLLM. FinTabNet TEDS improved from 23.4 to 81.1 in their evaluation. The article's existing production service and this experiment are distinct; neither proves Munera's 32B capacity or French accuracy.
  • University of Washington, research: QLoRA's authors report 65B adaptation on one 48 GB GPU. This establishes their memory-saving method under their conditions, not a fit guarantee for our image/context workloads.
  • Microsoft, research: LoRA's published implementation reports adapter experiments on RoBERTa, DeBERTa and GPT-2, with checkpoint reuse. These are supporting method results, not a production deployment of our selected models.

Qualification gate: run the stated profile through training, save/reload and evaluation; record peak CPU/GPU memory, actual checkpoint bytes, quality and one/four-request latency. Use the shared one-GPU pilot first. The allocations above are conditional procurement scenarios until those measurements pass.
