Ingress, egress and private network charges

Incoming bytes are generally free, but processing/storage operations may be charged. Same-region GCS reads generally avoid transfer charges; cross-zone VM traffic is typically $0.01/GiB, North American inter-region transfer $0.02/GiB, and low-volume internet export approximately $0.12/GiB. PSC service endpoints typically add $0.01/endpoint-hour and $0.01/GiB processed in both directions. The global Google APIs PSC bundle has no PSC data fee; PSC interfaces have processing fees but no hourly interface fee. Open-source software does not waive these network charges.

2. Qualifications for every accepted document

A PDF is eligible for training only after permission, lineage, input and label checks pass. A difficult or unreadable page may remain as a deliberately labelled abstention case; it must not be given an invented answer.

  1. Permission and provenance. Record source ID, checksum, project/tenant, issuer, version/date, permitted training/evaluation use, residency and retention. Keep annotation and model-assisted labelling inside the approved perimeter; no unapproved external API uploads.
  2. Coverage labels. Record document type/schema, French/English/bilingual status, template/issuer, digital versus scanned origin, page count, scan quality, tables and rare conditions. Track missing fields, conflicting values, amendments and genuinely unanswerable cases. Do not substitute thousands of near-identical invoices for coverage.
  3. Stable input preparation. Retain original PDFs and version rendering/OCR code, page order, crop transforms and resolution. Train on the input quality production will see. Keep manually corrected-text evaluations as a separate diagnostic, not the production score.
  4. Reviewed labels. Store schema version, raw and normalized field values, units/currency, and field-level evidence (page + text span or bounding box). Define absent, illegible, conflicting and not-applicable outcomes. Preserve source inconsistencies; do not silently “fix” totals or dates in gold extraction labels.
  5. Human qualification. Calibrate reviewers on a first 100-document batch; measure disagreements and adjudicate them. Independently second-review the locked test set and critical financial/legal fields. Proposed training QA: second-review at least a random 20% sample plus disputed/high-risk cases; expand review if disagreement is material. Model-generated labels are drafts, not ground truth.
  6. Leakage control before augmentation. Deduplicate exact and near-duplicates. Group pages, chunks, revisions, translations and synthetic derivatives by original lineage; split by project/issuer/time as appropriate. Hold out unseen projects/templates where generalization is required. Never mine training negatives or synthetic prompts from the locked test.
  7. Model-ready record. Include input text/image references, instruction/schema and reviewed target in the selected trainer's JSONL format. Log processor-expanded input length, target length, image tokens and truncation. Chunk with enough evidence; never require an answer whose source was cut away. Freeze tokenizer, chat template, preprocessing and dataset revision.

Acquisition allowance: at an assumed 80% acceptance rate, source 12,500 candidates to obtain 10,000 accepted extraction documents. This is not an observed rejection rate. Existing approved documents can satisfy that pool; it is not automatically new collection.

3. Extraction quality is separate from process validation

Keep the 22 deterministic reconcilers in code. The model extracts evidence-backed facts; rules perform joins, dates, thresholds, presence checks and arithmetic. Temporal remains the application workflow engine. None of these rules requires an additional LLM training corpus.

Proposed rule-test allowance: 20–50 meaningful cases per reconciler = 440–1,100 cases. Include correct matches, true mismatches, values below/at/above boundaries, missing/conflicting evidence, wrong entity/currency/unit/version, duplicates and out-of-order documents. These are regression fixtures, not SFT examples; branch coverage and risk may require more.

For cross-document processes, retain reviewed bundles and expected pass / fail / insufficient evidence outcomes. Test rules with gold facts first, then the complete pipeline from original documents. Reuse source files without leaking test bundles into training.

GateEvidence required before promotion

Statistical limit: with zero failures in 300 independent, representative cases, the one-sided 95% upper failure bound is still about 1%; approximately 3,000 zero-failure cases are needed for a 0.1% bound. Calculation: upper = 1 − 0.05^(1/n). Correlated fields/pages are not independent cases, and an overall sample does not certify rare document types. Repeatedly tuning against a test set invalidates its held-out role.

OVH + GCP Deployment

Status: proposed implementation specification; not a deployed system, compliance attestation, capacity reservation, or training-readiness approval. Revised 28 October 2026: the data lake stays in Google Cloud Storage and OVH no longer hosts canonical data.

Primary decision: keep the existing Google Cloud Storage lake in Montréal (northamerica-northeast1) as the only copy of documents and everything derived from them, and quantify invoice data readiness before allocating training GPUs. OVH runs only the coordination plane: Airflow, its PostgreSQL metadata and the MLflow tracking server. Coordination passes SHA-256 document IDs, release IDs and manifest URIs, never document bytes, text, labels or signed URLs. GCP supplies CPU preparation and bounded, on-demand GPU execution next to the data. MLflow tracks experiments; Airflow coordinates work; neither replaces document review or dataset governance.

Configuration: MLflow tracks experiments. Version-controlled YAML defines workload configuration consumed by reviewed launcher code; Airflow DAGs remain versioned Python DAGs.

2. Target topology and trust boundaries

OVH services hold no document bytes, page images, extracted text, labels, signed URLs or Google service-account keys. They obtain short-lived Google credentials through Workload Identity Federation and may only submit and inspect jobs and read release and completion manifests. GCP jobs receive no OVH administrative, database or MLflow credentials and never call OVH: they read approved inputs in place and write only their assigned run outputs, including a completion manifest that Airflow reads and records in MLflow.

A compromised coordination plane therefore exposes job metadata and the ability to launch reviewed recipes, not the corpus, provided jobs can run only pinned images from a registry the coordinator cannot write to and job workers have no internet egress (section 8). There is no staging copy and no import step: the release in GCS is the job input, and run outputs stay in GCS. Temporary resources are not deleted merely because the training process exited.

4.2 Catalog contract

5. Data discovery and preparation experiment

5.1 First questions to answer

  • How many unique, source-linked, permitted invoices exist, rather than objects or extraction rows?
  • Which are native-text PDFs versus scans/photos? Which languages, vendors, templates, page counts and quality levels occur?
  • Which fields are actually present and readable? How often are pages or attachments missing?
  • How much usable text is obtained without OCR? What is the incremental value and cost of OCR?
  • How much human correction is required, by field and document stratum?
  • Which existing human reviews are recoverable and trustworthy?

Do not collapse these into a single unexplained quality score.

5.2 Preparation stages

  1. Accession: register authorized source objects in place; do not copy, modify or delete them. Verify each SHA-256 against its archive name and record landing and archive generations. Record fixtures and unreachable links as separate categories.
  2. Safety validation: MIME sniffing, file integrity, malware checks, encrypted-file handling and bounded archive/PDF decoding. Unsupported or suspicious files remain quarantined with reasons.
  3. Lightweight corpus profiling: deduplication, page count, language/layout indicators, embedded-text presence, invoice/attachment classification and provenance completeness. Classification predictions remain provisional.
  4. Representative preparation sample: proposed initial working batch of up to 50 unique invoices, selected across available languages, scan quality, page count and vendor/layout families. This is a planning batch, not a statistical guarantee. Include difficult cases rather than selecting only clean text PDFs.
  5. Paired preparation comparison: embedded text alone versus embedded text plus OCR where warranted; preserve original images and page order. Record OCR engine/version, rendering settings, coordinates and time/memory/scratch usage. Apply deskew/rotation/cleanup only as versioned derivatives; never overwrite evidence.
  6. Review calibration: proposed up to 20 documents independently reviewed by two people, then adjudicated. Record disagreements and correction time. Increase sampling where disagreement or coverage gaps remain. Do not extrapolate a deliberately difficult sample to the entire corpus without weighting by the measured strata.
  7. Preparation decision: retain the least costly route that preserves required evidence and meets a documented, task-specific readability/labeling standard. Route difficult documents to manual repair, alternate preparation or exclusion with a reason; do not silently discard them.

All initial parsing/OCR runs in GCP Montréal next to the data. A cloud OCR API, model-assisted cleanup, or human annotation vendor requires a separate data-use decision. Generated text must not replace the original evidence.

5.3 Invoice schema and annotation rules

Version the extraction contract before mass annotation. Cover supplier/customer, invoice number, issue/due dates, currency, purchase-order references, subtotal, discounts, tax components, total, amount due, and repeatable line items (description, quantity, unit, price, tax and amount).

Store raw source values separately from normalized values; money uses decimal strings with explicit currency. Distinguish absent, unreadable, ambiguous and not-applicable fields from empty strings. Preserve page/region or text-span evidence. Multiple invoices in one PDF receive explicit child identities without splitting related examples across dataset partitions.

Arithmetic checks produce discrepancy flags, not “corrected” ground truth. Do not infer tax identifiers, missing dates or amounts merely to satisfy a schema. Record draft model/version/prompt if machine-generated labels are used; retain that provenance after human correction.

6. Dataset releases and evaluation contract

A training release requires all included examples to have readable source evidence, traceable preparation, approved annotation revisions, valid use permissions, a declared schema and reproducible split membership. Zero fixture records and zero known cross-split duplicate-family overlaps are allowed. Invalid examples are excluded with reasons rather than causing silent truncation or substitution.

Canonical labels are provider/trainer-neutral JSON; manifests and analysis tables can be JSONL/Parquet. Images are referenced as versioned objects, not embedded repeatedly as base64 in every table. Generate the selected trainer's conversational format from canonical labels and record the converter version.

Choose split strategy before tuning. Hold out document families and relevant project/vendor/layout groups; random page splits are prohibited. Select exact proportions after available group counts are known. A very small corpus may support a development/calibration release but cannot support a credible broad-generalization claim. Keep the final test set inaccessible to routine training jobs and obtain predictions through a separate evaluation identity/job.

Evaluate approved output JSON with schema validity, normalized field precision/recall or exact match as appropriate, amount/date/currency correctness, line-item alignment, missing/unsupported value rates, and source attribution. Report per-stratum results, sample sizes and uncertainty. Separately measure runtime, throughput, peak VRAM, failure rate and cost/document. Human or model-grader preference alone is not a substitute for field evidence.

7. MLflow, Airflow, and YAML responsibilities

7.1 MLflow on OVH

Deploy after upload and provenance work, initially to record preparation comparisons and baseline evaluations; it need not wait for fine-tuning. PostgreSQL holds the metadata. Artifacts live in a Montréal GCS bucket: Airflow creates each run, GCP jobs write artifacts directly to that run's artifact location, and the tracking server runs with --no-serve-artifacts, so it never proxies or stores artifact bytes. The server has no access to the artifact bucket: people open artifacts in GCS under their own IAM, and the MLflow UI artifact browser is not used in the pilot. Granting the server read access would let artifacts transit OVH, and adapters can memorize training data, so that requires an explicit decision.

Record dataset release/hash, schema/preparation/config/code revisions, model/processor revision, trainer/container digest, run type, provider job IDs, resource recipe, measured metrics and artifact checksums. Model versions link adapters to the exact base and quantization recipe; an adapter is not a standalone checkpoint.

Restrict the initial MLflow instance to one authorized research trust group. Experiment names are not a tested multi-tenant security boundary; artifact access is enforced by GCS IAM per bucket or prefix. Keep sensitive raw documents out of run parameters, tags and logs. Test artifact authorization, the largest intended upload, interrupted transfer, timeout and restore before relying on it for checkpoints.

7.2 Airflow on OVH

Add after the manually exercised preparation/release contract is stable. Start with a capped LocalExecutor for lightweight coordination; do not parse documents or train on the scheduler. LocalExecutor uses scheduler-side processes, so concurrency must be bounded. Use separate SQL database/user and an operator-only UI. Tasks call Google APIs with short-lived federated credentials (section 8) to submit Cloud Run or Batch jobs, poll their state and read completion manifests; they never read originals or prepared text.

Versioned DAG responsibilities:

  • invoice_profile: select an authorized accession snapshot, request preparation work, collect manifests and publish a readiness report.
  • dataset_release: validate approved revisions, rights and split constraints, then publish a frozen release. Human approval is an external prerequisite, not an unattended DAG task.
  • model_evaluate: select the evaluation inputs, execute the chosen recipe in GCP, validate outputs and publish metrics.
  • model_finetune: require an approved training release and qualified model recipe, grant the job only train/validation splits, run training in GCP, register checkpoints and evaluate a candidate under separate test access.

Pass SHA-256 document IDs, release IDs and manifest URIs through task metadata/XCom, never document bytes, file names, extracted text, signed URLs or model weights. Default to one paid GPU job at a time. No automatic repeated paid training attempts in the pilot: failures preserve evidence and require an authorized decision to rerun/resume.

8. GCP execution and cross-cloud control

Use Google Cloud Batch for GPU jobs, and Cloud Run jobs or Batch for CPU preparation: Airflow manages workflow dependencies; GCP provisions and runs the resources next to the data. Batch is not Vertex AI batch prediction, a persistent serving platform, or the fine-tuning algorithm.

Execution sequence:

  1. Operator selects an approved release and qualified recipe; the preflight checks permissions, region/zone, quota, capacity feasibility, price estimate, wall-time and output limits.
  2. Airflow creates the MLflow run and assigns its output prefix in the artifact bucket.
  3. Airflow submits the job under a dedicated runtime service account. The submitting identity is separate from the runtime identity and may attach only that runtime account.
  4. The job reads the release manifest and its permitted splits in place from GCS; training receives no test labels. Reusable model weights and pinned containers come from an authorized Canadian cache filled by a separate import job, not streamed per run.
  5. The job writes checkpoints, metrics and a completion manifest (files, sizes, SHA-256) to its assigned prefix. It never calls OVH.
  6. Airflow polls job state, validates the completion manifest, and logs metrics, parameters and artifact URIs to MLflow.
  7. Mark the logical run complete only after artifacts are verified and registered. Remove temporary resources according to policy, including failed-job cleanup and retained diagnostics.

A job restart must not silently create a second paid logical run: persist provider job IDs and inspect existing state before resubmission. Never trust an unverified success marker alone. Avoid loading arbitrary pickle or executing model code while validating artifacts.

Identity. OVH services obtain short-lived Google credentials through Workload Identity Federation. OVH VMs cannot natively prove their identity to Google, so use federation with X.509 certificates issued by a certificate authority we control, one client certificate per service. The pool, provider, attribute mapping and certificate rotation are deployment prerequisites, and the Security Token Service API must be enabled first. Do not use service-account keys, personal gcloud refresh tokens, or credentials pasted into chat.

9. Qwen3.5-122B-A10B qualification gate

SFT with QLoRA remains the intended experiment, not an already validated recipe. Preserve text and images so the data lake does not lock the task into text-only training.

Evidence from the earlier model review: Axolotl publishes an exact-model text-only QLoRA configuration with explicit MoE expert quantization, but no measured peak VRAM for that recipe; Unsloth warns about Qwen3.5 4-bit training and recommends BF16 LoRA. These sources disagree on the preferred approach. No successful full-model multimodal QLoRA training run was established in this project.

Before choosing GPU quantity, demonstrate on representative inputs:

  • Correct expert quantization, intended trainable parameter coverage including appropriate hybrid-attention components, and a real forward/backward/optimizer step.
  • Correct prompt/padding loss masking and supervision of approved JSON output, without fabricated reasoning targets.
  • Actual expanded context/image limits; no silent document or target truncation.
  • Checkpoint save/resume and fresh-load equivalence within the declared tolerance.
  • Peak VRAM/RAM/scratch, runtime and cost on the exact container/model/processor/resource configuration.
  • Base-model versus quantized-base versus adapter evaluation to distinguish quantization damage from training benefit.

The earlier single-H100 CPU-offloaded inference smoke is not training-fit evidence. If the requested multimodal QLoRA path fails qualification, present the measured limitation and alternatives for an explicit decision; do not silently switch to text-only, a smaller model, or BF16 LoRA.

10. Security, compliance, recovery, and spending boundaries

  • Issue dedicated, scoped deployment credentials and rotate/revoke superseded credentials before deploying shared services. Put new scoped credentials in the selected secret-management mechanism, not this document, Git, YAML values, container images or notebooks. Google access from OVH uses federation only.
  • Keep all document data, derivatives, catalog content, releases, artifacts and backups in GCP Montréal, or another approved Canadian GCP region where GPU capacity requires it. OVH Beauharnois holds coordination metadata only: job state, metrics, IDs and URIs. The review app's Firestore database in nam5 is the known exception to fix. Control-plane metadata and provider support access have separate residency implications that require review; a regional bucket is not proof that every operational datum stays in-country.
  • Obtain OVH SOC 1 Type II and SOC 2 Type II reports for Public Cloud and Private Cloud separately; prioritize explicit Public Cloud BHS compute scope, since OVH object storage is no longer used. A US SOC 3 report or Private Cloud report is not a substitute. Obtain applicable GCP reports/bridge letters and review service/regional scope for Cloud Storage, BigQuery, Cloud Run and Batch. Pending provider evidence is a tracked risk, not a declaration of non-compliance or approval.
  • Synthetic/non-sensitive deployment checks can proceed while evidence is collected. Real client-document onboarding requires the responsible data/security owner to approve access, retention, use rights and any unresolved provider risk.
  • Back up the OVH PostgreSQL (Airflow and MLflow metadata), the catalog and deployment configuration with separate backup credentials to a verified Canadian failure domain. The originals archive is versioned and retention-protected but still a single bucket in one region; decide whether originals need a second Canadian copy. Same-site versioning alone is neither independent backup nor geographic recovery.
  • Proposed controlled-pilot recovery targets: RPO up to 24 hours for metadata and RTO one business day, subject to owner acceptance and a successful restore exercise. Preserve or reconstruct acknowledged uploads through accession/object reconciliation; do not claim these targets as achieved.
  • Bound retention for logs, traces, scratch, failed outputs and temporary resources. Landing objects are deleted at 90 days only after their originals are archived; the evaluation copy expires at 120 days. Do not log invoice text, credentials or signed URLs by default. Deletion/withdrawal must account for releases, downstream copies, backups and the archive retention policy.
  • Account separately for the OVH coordination VM, block storage and backup; GCS, BigQuery, Cloud Run/Batch CPU and GPU, and caches; network transfer; software/support; and human annotation. Cross-cloud traffic is control-plane calls and small manifests, not data. No unquoted Private Cloud commitment is required for this minimal architecture.
  • Use runtime/task limits, admission authorization and concurrency caps for cost control. Billing alerts are delayed notifications, not guaranteed termination. Confirm teardown of chargeable resources after each qualification.

The existing experiment notebook is not a durable platform host. Before stopping/deleting or repurposing it, verify its actual state and preserve any required artifacts; a stop request is not proof that billing has ended. Do not retain its GPU merely to run MLflow.

12. Operational acceptance scenarios

These are required deployment checks, not tests already executed:

  1. Upload, preview, correct, approve and export one multi-page invoice end to end, with source evidence and user identities preserved.
  2. Submit an identical file twice: deduplicate canonical bytes while retaining both authorized accession records; deny cross-client information leakage.
  3. Interrupt an upload or parser: no partially prepared document or dataset release is published; the failure remains visible.
  4. Upload a corrupt/encrypted/oversized document: quarantine or bounded rejection with a reason; no scheduler/SQL exhaustion.
  5. Change an approved label: existing release remains reproducible; a new approval/release is required for revised data.
  6. Attempt anonymous access, another project's object, an expired signed URL and a privileged operation as an uploader: all denied with appropriate audit evidence.
  7. Restore catalog and selected source/annotation/release objects into an isolated environment; verify hashes, permissions and source-to-label lineage.
  8. Run a real CPU job submitted from OVH: inputs read in place, identical results, MLflow metadata pointing to GCS artifacts, job-state handling and removal of temporary resources; the OVH identity's read of an original is denied.
  9. Terminate a training qualification job: preserve valid checkpoint/diagnostics, prevent duplicate automatic paid execution, and verify resource cleanup.
  10. Reload the saved adapter with the pinned base/processor and evaluate the frozen examples; distinguish serialization success from acceptable extraction quality.
  11. Leave a landing object unarchived until the reconciliation threshold: the reconciliation fails loudly well before the 90-day deletion.

High — originals retention The archive's 7-year policy is not locked; archived client originals cannot be deleted per object before 2033 Data owner confirms retention against client agreements before anyone locks the policy
High — artifact authorization The MLflow server has no artifact access; GCS IAM governs artifacts per bucket or prefix One trust group initially; prove prefix-level authorization before adding mutually isolated clients
High — model runtime Exact multimodal QLoRA fit is unproven and published guidance differs Preserve intended task; qualify before GPU commitment; model owner decides alternatives only on evidence
High — sensitive-data onboarding Provider Public Cloud scope, use rights and retention approvals remain outstanding Obtain applicable evidence or documented risk acceptance; no implicit compliance approval
Medium — automatic archiving The upload trigger is not deployed; new uploads are neither processed nor archived automatically Phase 1 deploys promotion and reconciliation before new uploads are accepted
Medium — recovery Single-VM coordination plane and single-region lake Accept non-HA pilot explicitly; back up PostgreSQL off the VM; decide on a second Canadian copy of originals
Medium — capacity and cost Preparation effort and GPU allocation are unknown Measure representative work, quote actual configurations, gate paid runs; no speculative TB or H100 purchase
Medium — operational complexity Cross-cloud control adds federation, certificate rotation and API failure handling Start with a CPU end-to-end proof; keep data and execution in GCP so no cross-cloud data path exists
Open — ingestion sources Client uploads, connectors to client systems and crawling are not chosen Each writes directly into landing; connector and crawler workers run in GCP
Deferred — Firestore nam5 The review app's database is in a US multi-region; a Firestore location cannot be changed in place Separate change: new Canadian regional database, export/import, repoint the review app and its trigger
Deferred — untracked bucket The evaluation copy is outside Terraform and deletes its corpus copy at 120 days Bring under Terraform or retire
