1. Framework: three maturity levels

Google's reference architecture defines Level 0: manual, Level 1: ML pipeline automation, and Level 2: CI/CD pipeline automation. Level 1 reuses the pipeline implementation across experimentation and production. Level 2 additionally builds, tests and deploys pipeline components through CI/CD. The article supports gradual adoption; it prescribes neither a twelve-month programme nor a fourth maturity level.

P0–P5 are Munera delivery labels, retained from the supplied perimeter design. They must not be presented as Google's numbered levels or as completed deployments.

The original diagram places identity, egress controls, residency, immutable audit storage and logs around every level. Their implementation and review ownership are tracked in the infrastructure document.

2. Read the complete architecture

The diagram retains the Google Figures 3–5 relationships: an experimentation lane and production lane; extraction → data validation → preparation → training → evaluation → model validation; source/configuration; pipeline deployment; registry; metadata; serving and monitoring feedback. A feature store is optional. Scheduled, new-data, degradation and drift triggers can already occur at Level 1.

Munera's existing pipeline design assigns Airflow to training orchestration and Temporal to application document workflows. Git holds code/configuration, DVC identifies datasets, and MLflow tracks runs and registered releases. These assignments describe the supplied architecture; they do not establish that all integrations run today.

The September 23 handoff contains conflicting historical readiness claims. B2 preserves six ML stages and twelve operational Airflow tasks as different levels of detail, keeps Airflow separate from Temporal, and uses restart-based production rollout. Its cockpit, branch and defect claims are dated observations, not a fresh code audit. Releasing a GPU job does not end a dedicated-host billing commitment.

Two corrections matter when reading the older diagrams:

  • Registry promotion and serving deployment are separate operations. MLflow aliases name registered versions; the supplied design separately specifies a serving rollout. vLLM's LoRA interface loads adapters through serving configuration or explicit runtime management.
  • Deferring drift triggers to P5 is a Munera sequencing choice. It is not a requirement of Google's Level 1 definition. Labels such as “MET by construction” in the August design describe intent and must not substitute for execution evidence.

4. Evidence about effort, limits and hardware

Hidden Technical Debt in Machine Learning Systems identifies data dependencies, feedback loops, configuration and integration costs. It is systems analysis, not a staffing calculator. The production-pipeline study examines opportunities to avoid repeated computation; its reported savings cannot be booked as a discount against this project's bill.

The reviewed publications provide no transferable percentage for Munera's engineering overhead, completion schedule or GPU utilization. Nor does the Google framework specify a GPU SKU, physical-host count or storage allocation. Hardware figures belong to the workload requirements and shared infrastructure, with commercial configurations separately recorded in pricing.

Still unmeasured for Munera: scientist/platform time per experiment; queue delay; peak host RAM and VRAM; training duration; concurrent serving latency; artifact growth; restore time; and promotion/rollback behavior. These are open validation requirements—not estimates disguised as researched facts. The complete architecture is a record of intended responsibilities and flows until those tests produce evidence.

Capacity follows workload, not maturity level

Provider update — 24 September 2026. Automation maturity does not itself multiply GPUs or storage. A shared-worker lab can run the four model families sequentially; independent inference, application HA and geographic recovery are separate procurement states. The Hypertec/Micrologic pricing guide maps demo, experiments, rehearsal, production, recovery, distributed scale and closeout without inventing dates or a twelve-month project. Prices remain quote-required. The infrastructure guide retains service allocations and trust boundaries.

Qualification and budget gates

Introduce the software/hardware qualification gate before a GPU commitment, and require production-volume inputs before turning a shared training worker into a serving claim. Record board edition/power cap, driver/CUDA/torch, quantization/preparation dtypes, attention and PW hybrid kernels, then perform train/save/reload, inference, denied-egress and restore checks. Blackwell support in PyTorch, bitsandbytes build support.

Request a scoped qualification estimate under the pricing guide. MIG concurrency requires actual-recipe and sandbox compatibility tests.

Each family records reproducible work units. Forecast hours from recipe-matched measurements. The pricing guide’s 50/100/250 GPU-hour cases are spend sensitivities, not predicted monthly demand.
